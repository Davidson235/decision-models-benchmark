## 3. Проблемы

### P1. `pip install` зависает на резолве зависимостей (блокирующая)

**Симптом.** `pip install laya` висит 50+ минут: CPU занят на 100 %, размер
pip-кэша не меняется, в выводе остановка после `Requirement already satisfied: torch`.
То же с `pip install transformers safetensors huggingface_hub numpy`.

**Что пробовал:**
- `--only-binary :all:`, `--timeout 60 --retries 2` — не помогает;
- установка torch с `--index-url https://download.pytorch.org/whl/cpu` **сработала
  за минуту** (124 MB), то есть сеть и pip исправны, проблема именно в резолве
  (перебор версий/зависимостей).

**Обход, который работает:** скачать точные wheel-файлы через PyPI JSON API
(`https://pypi.org/pypi/<pkg>/json` → `urls[]` → прямой URL колеса) и ставить
локально: `pip install --no-index --find-links .tools/wheels --no-deps <pkg>`.
Скачивание 15 колёс заняло секунды.

**Побочный эффект:** убитые задачи оставляли осиротевшие `pip`-процессы, один
накрутил 9797 секунд CPU и мешал остальному. Пришлось убивать вручную через
`Get-CimInstance Win32_Process`.

**Вопрос:** есть ли надёжный способ заставить pip не резолвить (например,
`--no-deps` для всего дерева сразу, или `uv pip install`)?

### P2. `huggingface_hub 2.3.0` тянет нестандартные зависимости

**Симптом.** `import huggingface_hub._snapshot_download` падает по очереди:

**Вопрос:** это баг сборки hub 2.3.0 или ожидаемое поведение? Не сломается ли
что-то ещё при первом реальном вызове?

### P4. torch без CUDA

**Факт.** `torch 2.14.1+cpu`, `torch.cuda.is_available() == False`.

**Причина.** CUDA-колесо (~2.5 GB) тянет `nvidia-*`-пакеты, и pip на них
зависает (см. P1). Поставил CPU-версию, чтобы двигаться дальше.

**Следствие.** Laya будет считать на CPU. Для 322M-энкодера это терпимо
(ожидаемо 50–150 мс), но GPU простаивает.

**Вопрос:** как поставить CUDA-torch в этом окружении, не попадая в резолвер?
Прямая ссылка на конкретный `.whl` из `download.pytorch.org` под cp312 и
win_amd64 — какой файл брать для torch 2.14.1 + CUDA 12.4?

### P5. Загрузка весов Laya Multilingual встала (текущий блокер)

**Симптом.** `laya.load("convaiinnovations/laya-multilingual")` доходит до
`snapshot_download` и **зависает**: за 30 секунд в кэш добавлено 0 байт,
`.incomplete`-файл нулевого размера, процесс python висит без CPU-нагрузки.

**Данные:**
```

*.incomplete  0.0 MB
delta за 30 с 0.00 MB
```

**Что пробовал:** `HF_HOME` внутрь проекта (P3), отключение прогресс-баров,
убийство конкурирующих pip-процессов. Не помогло.

**Гипотеза (не проверена).** `httpx2`/`httpcore2` в hub 2.3.0 некорректно
работают с этим прокси/сетью, и большие файлы не начинают качаться, тогда как
обычный `curl` с той же машины льёт 5.5 MB/s.

**План обхода, который ещё не выполнен:** скачать файлы репозитория `curl`-ом в
локальную папку и вызвать `laya.load("<локальный путь>")`, полностью минуя
huggingface_hub.

**Вопрос:** правильный ли это путь, и какие именно файлы нужны `laya.load`
кроме `model.safetensors`, `config.json` и токенизатора?

### P6. Для Laya Multilingual нет GGUF, совместимого с llama.cpp

## 7. Применённые решения (после консультации)

### P5 — РЕШЕНО

Скачивание всего репозитория `curl`-ом и загрузка из локальной папки работает.
`huggingface_hub` действительно не нужен: с `HF_HUB_OFFLINE=1` `laya.load(<путь>)`
читает файлы напрямую.

```powershell
pwsh -File .tools\fetch_laya.ps1          # 8 файлов, 646.8 MB, SHA256 сверен
$env:HF_HUB_OFFLINE = "1"
.\.venv\Scripts\python.exe .tools\laya_smoke.py
```

Замеры: загрузка **6.7 с**, предсказание **78 мс** (p50 на CPU, 322M энкодер).
Состав репозитория: `model.safetensors` (614 MB), `tokenizer/tokenizer.json`
(32.8 MB), `encoder/config.json`, `rl_agent_config.json`, `config.json`.

`dict` и JSON-строка в `state` дают **идентичный** результат — формат входа не
был причиной низкого качества.

### Качество Laya Multilingual: 0.383

| Метрика | Значение |
|---|---|
| Точность | **0.383** (95% CI 0.30–0.48) |
| Brier | 0.866 |
| ECE | 0.282 |
| p50 | 78 мс |
| Ошибок | 0 |

Это уровень случайного выбора для 4–7 вариантов. По семействам: `choice_fact`
0.333 (три варианта — ровно шанс), `score` 0.15, `multilingual` 0.571.

Для сравнения на том же корпусе: Laya EN — 0.514, `vllm-d3-mini` — 0.850.
Консультант предсказывал «около 0.352 zero-shot» — совпало с точностью до 3 п.п.

Причина видна на примерах: модель уверенно отвечает неверно
(`CH-001`: валидный payload → `entity_not_found` с p=0.946) и при этом даёт
корректные ответы на простых формулировках (`ML-001-RU`: refund, p=1.0).
То есть это узкий дообученный роутер, а не универсальный классификатор —
ровно как написано в карточке модели.

### P4 — признано неактуальным

CUDA-колесо для torch 2.14 существует в вариантах `cu126` и `cu130`
(`torch-2.14.1+cu126-cp312-cp312-win_amd64.whl`, 2.6 GB). Но Laya на CPU даёт
78 мс на предсказание, поэтому 2.6 GB трафика ради ускорения уже не нужны.
Ставить имеет смысл только если понадобится батчевая обработка.

## 8. P7, P8 и P9: результаты экспериментов

### P7. `-ub`, контекст и KV-квантование

Все замеры на `vllm-d3-mini`, 60 задач, одна сессия, одинаковые условия.

| Конфигурация | VRAM | p50 | p95 |
|---|---|---|---|
| `-c 4096 -ub 4096` | 6503 MiB | 187 мс | 281 мс |
| `-c 4096 -ub 1024` | 6693 MiB | 203 мс | 265 мс |
| `-c 8192 -ub 4096` | 6499 MiB | 188 мс | 312 мс |
| `-c 2048 -ub 4096` | 6517 MiB | 187 мс | 297 мс |
| `-c 8192 -ub 1024` | 6696 MiB | 141 мс | 219 мс |

**Вывод: `-ub` не помог.** Память не уменьшилась (наоборот, +190 MiB), задержка
не улучшилась — разброс 141–203 мс не коррелирует с ubatch. Совет «начните с
`-ub`» на этой сборке не подтвердился.

Длина контекста на задержку тоже не влияет (187–188 мс при 2048 и 8192).

**KV-квантование — единственное, что дало эффект.** Без него `d3-flash` при
`-c 8192` не загружается вообще:

```
common_fit_params: failed to fit params to free device memory
```

С `-fa on -ctk q8_0 -ctv q8_0`:

| Конфигурация | VRAM | p50 | p95 | Точность |
|---|---|---|---|---|
| `d3-flash -c 8192 -ub 1024 -kv q8` | 7628 MiB | 297 мс | **12 641 мс** | 0.900 |
| `d3-flash -c 8192 -ub 4096 -kv q8` | 7584 MiB | 328 мс | **469 мс** | 0.900 |

Хвост в 12.6 секунды возник именно из-за `-ub 1024`, а не из-за квантования:
с `-ub 4096` p95 падает в 27 раз. Точность 0.900 против 0.895 у Q4 без
квантования — разница в пределах шума.

### P8. Привязка к ядрам

Одна сессия, три замера, GPU-модель `d3-mini`, CPU-модель `Kev-9B` на 8 потоков.

| Сценарий | p50 | p95 |
|---|---|---|
| GPU один | 203 мс | 297 мс |
| GPU + нагрузка CPU, без привязки | 188 мс | 282 мс |
| GPU + нагрузка CPU, P-ядра / E-ядра | 203 мс | 297 мс |

**Вывод: конкуренция за ядра не обнаружена.** Все три числа лежат в пределах
шума, причём «с нагрузкой» оказалось даже быстрее, чем «без». Гипотеза о +67 %
просадке из-за конкуренции за ядра не подтвердилась.

### Настоящая причина разброса задержек

Частота GPU во время прогона:

```
t+2s:  825 MHz, 28 %, 49°C
t+4s: 1935 MHz, 10 %, 51°C
t+6s:  855 MHz, 17 %, 49°C
t+8s: 1515 MHz, 39 %, 50°C
t+10s: 1470 MHz, 13 %, 49°C
```

Карта колеблется между 825 и 1935 MHz, потому что запросы короткие и между ними
есть паузы — устойчивый boost не включается. Отсюда и разница 94 мс против
188 мс на **одной и той же конфигурации** в разных сессиях.

**Следствие для методики:** любые сравнения задержек локальных моделей имеют
смысл только внутри одной сессии и после прогрева. Абсолютные числа между
сессиями несопоставимы. Стабилизировать можно через `nvidia-smi -lgc` (нужны
права администратора), но это повышает энергопотребление и температуру.

### P9-бис. Привязка CPU-инференса к P-ядрам

Проверено дважды: на реальном корпусе (25 задач) и на одинаковых коротких
запросах (20 повторов одной фразы). Одна сессия, прогрев 3 запроса, `Kev-9B` на CPU.

| Конфигурация | Корпус 25 задач: p50 / p95 | Одинаковые запросы: p50 / p95 |
|---|---|---|
| `-t 6 -C 0x555 --cpu-strict 1` | 1437 / **13 641** мс | **1116 / 1210** мс |
| `-t 12 -C 0xFFF --cpu-strict 1` | 1688 / 12 531 мс | 1406 / 1552 мс |
| `-t 14` без маски | 1469 / 11 281 мс | 1281 / 1405 мс |

**Что подтвердилось:** на однородной нагрузке 6 потоков на физических P-ядрах
действительно быстрее — 1116 мс против 1281 мс у `-t 14` (−13 %) и против
1406 мс у `-t 12` (−21 %). Переподписка потоков вредит.

**Что не подтвердилось:** предсказание «с маской p95 будет около 1500 мс, а без
маски 3000 мс». На реальном корпусе p95 составил 11–13 секунд при **всех трёх**
конфигурациях, включая маску. То есть хвост определяется не размещением потоков,
а отдельными длинными задачами: 25 выборок дают p95 по второму сверху значению,
и одна тяжёлая задача его определяет.

**Практический вывод:** `-t 6 -C 0x555 --cpu-strict 1` даёт стабильные ~13 % на
CPU-инференсе и стоит того как настройка по умолчанию. Но p95 по смешанному
корпусу этим не лечится — для честной оценки хвоста нужны p90 на ≥50 задачах
или отдельный замер по классам длины.

**Задержки в «чистых» условиях оказались выше, а не ниже.** Значит браузер не
был причиной быстрых чисел ранее: разброс даёт состояние буста GPU и состав
прогона, а не фоновая нагрузка. Абсолютные миллисекунды между сессиями
по-прежнему несопоставимы, сравнивать можно только внутри одной сессии.

### Настоящая причина провалов по скорости — переполнение VRAM

Clef-Flash при -c 4096 занимает 7686 MiB из 8192 и начинает свепить:
300 секунд на запрос, сервер отменяет задачи по таймауту.

При -c 2048 та же модель: **7368 MiB**, 183–190 мс на запрос.

| Модель | Рабочий контекст | VRAM | Результат |
|---|---|---|---|
| Kev-9B | -c 2048 | 7675 MiB (332 своб.) | работает |
| Clef-Flash | -c 2048 | 7368 MiB (639 своб.) | 190 мс |
| vllm-d3-flash | -c 4096 + KV q8 | 7931 MiB (**76 своб.**) | работает, но на грани |
| остальные | -c 4096 | 2.4–6.5 GB | без проблем |

Оставлять меньше ~600 MiB свободными нельзя — начинается пейджинг и деградация
в сотни раз, а не в проценты.

### Что стоит применять на практике
| Изменение | Вердикт |
|---|---|
| `-ub` меньше 4096 | **не применять** — память не экономит, хвост p95 растёт |
| `-fa on -ctk q8_0 -ctv q8_0` | **применять** для моделей ≥6 GB: это единственный способ уложить их в 8 GB на 8K контексте |
| `-c` по потребности | влияет на VRAM, но не на задержку |
| `--cpu-mask` | **не нужен** — эффекта нет |
| Прогрев перед замером | **обязателен**, иначе числа гуляют вдвое |
